# 2.1 Exercises: git on your own machine

Practice for session 2.1. Everything here is local: no GitHub, no internet. We will do that in 2.2.

**Do each exercise twice: once at the terminal, once in GitStudio.** Not because you will use
both forever, but because it makes you understand the same action in both places. GitStudio
runs the commands you are typing.

Keep **GitStudio** open throughout. It is a visualisation plug-in that draws the git history
as it changes, and it also does the everyday work: staging, committing, switching branches,
discarding. Watch the graph redraw after every action, because that picture is the thing you
are learning.

**Do this in your own `ds2026` folder.** It becomes your repository today, and stays your
repository for the rest of the term: your labs, your project, everything will be committed here. 

The files you create below live in `week2/`, so nothing you break here touches your project.
2.2 connects this repository to GitHub.

Answers are at the bottom. Try first.

---

## 1. Turn `ds2026` into a repository

**Terminal.** Open a terminal in your `ds2026` folder, check you are in the right place, and
turn it into a git repository. Then ask git what it thinks the state of things is.

**GitStudio.** Open `ds2026` in VS Code and open GitStudio. It now has a repository to show
you: a list of files git has never seen, and an empty graph, because there are no commits
yet.

**Check.** Two things to look at before you go on:

- there is a hidden `.git` folder. Find it from the terminal. What happens to the repository
  if you delete it?
- `git status` does **not** list `data/` or `.venv/`. Why not? Open `.gitignore` at the root
  and find the lines responsible.

---

## 2. The first commit

Create a file `week2/notes.md` with a line of text in it.

**Terminal.** Check the status. Stage the file. Check the status again, and notice the
wording change. Commit it with a message.

**GitStudio.** Do the same for a second file, `week2/data-sources.md`, without touching the
terminal: find where GitStudio lists the changed file, stage it, write a message, commit.

**Check.** You now have two commits. Find them both in the GitStudio graph, and list them
at the terminal in one line each.

---

## 3. Staged and unstaged are different places

Edit both files, then stage **only** `week2/notes.md`.

**Terminal.** Run `git status`. Both files are listed, in two different sections. Then show
the changes that are staged, and separately the changes that are not.

**GitStudio.** The same split is on screen: files that are staged, and files that are
changed but not staged. Click a file in each group and read the diff.

**Check.** Which of the two files will be in your next commit? Commit, then confirm you were
right.

---

## 4. Reading your own history

**Terminal.** Show the history one line per commit. Then show which branch you are on and
where `HEAD` is pointing.

**GitStudio.** Find the same three things in the graph: the newest commit, the branch label,
and which commit that label sits on.

**Check.** In your own words, what is the difference between `main` and `HEAD`?

---

## 5. Branching

**Terminal.** Create a branch called `experiment` and switch to it in one command. Confirm
you are on it.

**GitStudio.** Switch back to `main` from GitStudio, and watch what moves in the graph as you
do. The commits do not move. Something else does.

**Check.** How many commits are on `experiment` that are not on `main`? (The answer right
now is zero. Make sure you can see why.)

---

## 6. Develop one branch

Switch to `experiment`. Add a third file, `week2/scratch.md`, and commit it.

Now switch back to `main` and look at your file tree.

**Check.** `week2/scratch.md` is gone. Where did it go, and why is this not data loss? Switch back
and confirm it returns.

---

## 7. Merging

Make the branches diverge: while on `main`, edit `week2/notes.md` and commit the change. Now
`main` and `experiment` each have a commit the other does not.

**Terminal.** Merge `experiment` into `main`. Pay attention to which branch you are standing
on when you run it.

**GitStudio.** Look at the graph. Two lines came together, and the commit where they join has
two parents, which no other commit in your history has.

**Check.** Could you have merged `main` into `experiment` instead? What would be different?

---

## 8. Undoing an edit you have not committed

Delete everything in `week2/notes.md` and save. Do not commit.

**Terminal.** Put the file back as it was at the last commit, without touching anything else.

**GitStudio.** Do it again, this time without the terminal: make another unwanted edit, then
find the discard control in GitStudio. It will ask you to confirm. Read what it says before
you click, because it means it.

**Check.** This is the one operation in this session with no undo. Why? What did git never
have a copy of?

---

## 9. Unstaging without losing work

Edit `week2/data-sources.md` and stage it. Then change your mind: take it out of the staging area
**without** losing the edit.

**Terminal.** One command.

**GitStudio.** Find the control that takes a file back out of the staged group.

**Check.** After unstaging, is your edit still in the file? Check before you believe it.

---

## 10. Undoing a commit, safely

Commit something you do not want: add a line saying `DELETE ME` to `week2/notes.md` and commit it.

**Terminal.** Undo that commit by making a new commit that reverses it. Do not delete
anything from the history.

**Check.** Look at the log. Is it shorter or longer than before? Why is that the safe
behaviour when other people have your history?

---

## 11. Writing messages someone can read

Look back at the messages you have written today.

Rewrite each one in your head to fit the rule from class: imperative mood, under about 50
characters, saying what the commit does rather than what you were doing.

- "updated stuff" becomes what?
- "fixed it" becomes what?
- "notes.md" becomes what?

**Check.** Run the one-line log and read it as if it were someone else's project. Can you
tell what happened without opening a single file?

---

## 12. Put it together, no hints

In one sequence, without looking anything up:

1. Make a branch called `cleanup`.
2. On it, delete `week2/scratch.md` and commit the deletion.
3. Merge `cleanup` into `main`.
4. Realise you wanted `week2/scratch.md` after all, and get it back without editing any file by
   hand.
5. Show the final history, one line per commit, with the branching drawn.

If you can do all five without hesitating, you have the local half of git. 2.2 adds
GitHub, and 2.3 is branching practice online.

# Answers

**1.** `cd` to your `ds2026` folder, `pwd` to check, `git init`, `git status`. The hidden
folder: `ls -a`. Deleting `.git` leaves your files and destroys the entire history: the folder
stops being a repository. `data/` and `.venv/` are absent from `git status` because
`.gitignore` lists them, which is why they never reach GitHub in 2.2.

**2.** `git status`, `git add week2/notes.md`, `git status`,
`git commit -m "Add project notes"`.
History: `git log --oneline`.

**3.** `git status`, `git diff --staged` for what is staged, `git diff` for what is not. Only
`notes.md` is committed, because only it was staged.

**4.** `git log --oneline`, and `git log --oneline --decorate` or `git branch` for where you
are. `main` is a pointer to a commit; `HEAD` is a pointer to the branch you are currently on.

**5.** `git switch -c experiment`, then `git branch` to confirm. Zero commits differ: a new
branch points at the commit you were already on.

**6.** `git switch main`. The file is in the commit on `experiment`, which `main` does not
point to. Nothing is lost; your working directory is just showing a different snapshot.

**7.** `git switch main`, then `git merge experiment`. Merging the other way round would move
`experiment` to include main's work and leave `main` where it is.

**8.** `git restore week2/notes.md`. There is no undo because the edit was never committed, so git
never had a copy to go back to.

**9.** `git restore --staged week2/data-sources.md`. The edit stays in the file; only the staging
changes.

**10.** `git revert HEAD`. The log is longer: revert adds a commit that undoes the earlier
one, rather than removing history that other people may already have.

**12.** `git switch -c cleanup`, `rm week2/scratch.md` or delete it in VS Code, `git add -A`,
`git commit -m "Remove scratch file"`, `git switch main`, `git merge cleanup`,
`git revert HEAD` (or `git revert <the deletion commit>`), then
`git log --oneline --graph --all`.
